# 南投客運官網盤點與潭行 Twin 整合提案

日期：2026-10-23｜對應 SPEC v0.2｜公開網站研究，尚未實作服務、訓練模型或接入訂位後台。

## 1. 結論

官網能補上刷卡資料所缺的「供給與營運規則」：方向化路線、班表、營運日、預約與現場候補、站點位置說明、活動改道、票價與套票。專案可從歷史運量儀表板提升為「需求、服務規則、特殊事件與旅客轉乘共用同一模型的數位孿生」。

最有辨識度的功能應是：**在 GIS 上預演中途站客滿、預約座位保留、活動改道與高鐵轉乘風險，並比較可行的班次與旅客導流方案。**

## 4. 對原規格最重要的十個修正

### 4.1 部分缺日有了營運解釋

初查發現 2025-07-07 沒有刷卡紀錄；官網 2025-07-06 公告明示隔日因颱風全路線停駛。兩者吻合，應在營運日曆標記為「公告停駛」，保留交易日完整性檢查。[公告](http://www.ntbus.com.tw/news.html)

這不等於當天沒有人想搭車。模型需分開「潛在需求」與「因停駛而沒有搭乘紀錄」，不能把零交易直接拿去學正常需求。2024 五個缺日仍未由本次所讀公告證實原因。

### 4.2 子線停靠模式必須進模型

核心路線圖將 6670 B/F、E、A/D、C、H 以不同線色呈現；圖例及班表可辨認經埔里、繞九族、經暨大、延駛向山／機場、只至埔里等差異。需要再依方向、班次與生效期間核定，不可只用一條「6670」折線代表所有服務。[日月潭線](http://www.ntbus.com.tw/tour-sml.html)、[埔里總表](http://www.ntbus.com.tw/hsr6.html)

圖上有部分站間分鐘數，可作初始行程時間參考，但不是道路幾何、實測速度或旅行時間分布。圖片不可直接視為具地理座標的 GIS 路網。

### 4.3 九人座不等於九個可售乘客座位

官網另列九人座套票專車及其服務班次；幸福巴士另有一團最多 7 人等特定產品說明。車型字樣不是可跨產品套用的有效容量。需取得每車可載乘客席數、輪椅配置及行李限制。[日月潭線](http://www.ntbus.com.tw/tour-sml.html)、[幸福巴士訂位說明](http://www.ntbus.com.tw/bs-gono.html)

埔里簡圖文字也指出往臺中行駛國道班車禁止站立；模擬該服務不可用超出座位數的站立容量消化尖峰。[埔里簡圖](http://www.ntbus.com.tw/pulimap.html)

### 4.4 站點公平性比平均載客率更有意義

官網明示部分尖峰埔里往高鐵容易客滿，中間站旅客不易上車；日月潭起站客滿時，暨大旅客可先到埔里轉乘。[日月潭線](http://www.ntbus.com.tw/tour-sml.html)

因此新增「中途站被拒載風險／最大候車／是否能搭上末班」，比較終點站總量以外的服務差距。實際被拒載數尚未觀測，只能先模擬並另收集現場樣本校準。

### 4.5 座位應分成已占用、保留、可候補

日月潭線公告部分向山發車班次在日月潭站保留 10 席。訂票頁又載明報到與上車地點、前 20 分鐘報到、逾時改現場候位；部分連假不開放預約。[日月潭線](http://www.ntbus.com.tw/tour-sml.html)、[回程預約](https://ntbus.welcometw.com/tour/v2gb)

加入 seat_inventory、reservation_quota、checkin_deadline、boarding_stop_scope、standby_queue。保留 10 席不能再疊加另一份「預約配額」形成重複扣席，須確認兩者是否同一資源。沒有後台預約／核銷資料時，no-show 與釋位時間只能用情境假設。

### 4.6 班表與公車動態都可能缺加班車

國六總表說明「加」表示每日加班車，且公車動態無法顯示。最新公告也會新增或調整臨時班次。[國六總表](http://www.ntbus.com.tw/hsr6.html)

因此 GPS／動態缺資料不等於沒開車。供給來源需要區分 scheduled、extra、observed、reconstructed，並做票證車次與供給的對帳；不能只靠即時 API 當全部供給真相。

### 4.7 轉乘風險可成為旅客端核心

官網提醒中途站時刻為預估、道路壅塞時不保證能準時抵達高鐵。[日月潭線](http://www.ntbus.com.tw/tour-sml.html)

可做「預計高鐵發車時刻 → 建議公車與緩衝時間 → 改走埔里轉乘的候選方案」。尚無旅行時間分布與高鐵班表時，只顯示保守緩衝假設；待校準後才提供誤接機率，不能輸出未驗證的精確成功率。

### 4.8 一次完整旅行可能有多筆刷卡

清境無縫接駁頁說明在埔里更換路線、可免換車，電子票證需分段上下車刷卡。[清境接駁](http://www.ntbus.com.tw/cjfm.html)

因此應區分票證交易 leg、車輛服務 trip、乘客完整 journey 與實體換車 transfer。目前只有 6670 資料，不能聲稱已識別全程清境旅遊鏈；需補其他路線並驗證匿名連結規則。

### 4.9 「套票買了」不能推出「能搭上車」

套票與 FAQ 明載一般套票無劃位及優先乘坐權。商品內容可能是環湖券、單程車票或一日券，使用次數不同。[套票總覽](http://www.ntbus.com.tw/package.html)、[FAQ](http://www.ntbus.com.tw/callus.html)、[日月潭商品](http://www.ntbus.com.tw/p-1.html)

旅客助理應同時檢查票券適用性、可用班次、預約條件、兌換時間與回程；購票連結導向既有系統，不自行建立新的訂票平台。公開「參與人數／瀏覽數」不是即時座位庫存或實際每日搭乘量。

### 4.10 官網資訊本身需要版本與衝突治理

- 首頁輪播仍可見九族 910 元起的宣傳，2026 年商品明細頁列 1140 元；在不同年份／商品條件確認前不能挑便宜數字回答。[首頁](http://www.ntbus.com.tw/)、[商品頁](http://www.ntbus.com.tw/p-nine.html)
- 行程建議頁存在與年度商品頁不同的套票名稱／金額與班次建議，不能直接作為現在可執行行程。[行程建議](http://www.ntbus.com.tw/gotour.html)
- 網址名含 2016 的優惠頁，本文可能寫 2026，不能用 URL 年份判斷內容年份。
- 2026-09-20 泳渡公告的主表／文字分別出現九龍口、魚池國中等描述；需把方向、時段與上下車地點拆開，衝突處人工核對，不能自動選定一個終點。[公告](http://www.ntbus.com.tw/news.html)
- 某些幸福巴士預約說明同頁有「兩週內」及「兩個月內」文字，不能自動合成單一規則。[訂位說明](http://www.ntbus.com.tw/bs-gono.html)

## 5. 建議的產品增補

### P0：服務規則與事件驅動的 GIS 指揮台

在原規格加入：

1. **營運日曆**：一般日、週五至日、學期／寒暑假、活動日、停駛日，套用已確認規則。
2. **站點候車與保留座位**：分辨現場／已預約／已報到人數及可用席位。
3. **事件圖層**：停駛、繞駛、縮短路線、臨時站、加班與車輛不可用。
4. **轉乘風險比較**：日月潭直達、埔里轉乘、改時段等方案的總時間與風險。
5. **資訊品質面板**：有效日期、來源衝突、缺資料、需要業者確認的規則。

第一個情境建議：「假日午後日月潭回程集中，中途暨大旅客容易搭不上車，如何透過埔里轉乘、班次平移與加班改善？」這有官網描述的營運痛點，也有 6670 交易作需求基礎。轉乘替代線先使用公開班表，負載／轉乘成功率採明示假設，直到取得該線實際需求。

### P1：會考慮回程的智慧旅遊助理

輸入：出發站、日期、想去的景點、最晚回到高鐵時刻、同行條件與可接受步行量。

輸出三種候選：時間優先、較低擁擠風險、票券成本優先。每種顯示班次、報到時間、步行轉乘、票券使用、回程最晚離開景點時間。班船／纜車需要其最新班表與停駛資料才能納入可執行規劃，不能只靠套票包含某交通工具就假設隨時可搭。

### P2：小巴接駁與低碳公平服務

以幸福巴士作需求反應式服務研究，加入最少成行人數、可服務範圍、乘客與行李容量、駕駛勤務、固定接駁時窗。需先確認具體產品的有效規則；不能把觀光包車條款直接當一般 DRT 規範。

ESG 除車公里／排放強度，加入輪椅可達性、低量站最大候車、末班後未服務旅客。國道不站立、保留席位與無障礙設備應是服務限制，不是可以為了提高平均載客率而犧牲的項目。

## 6. 新增資料契約與計算規則

| 物件 | 關鍵欄位 |
|---|---|
| source_document | URL、擷取時間、checksum、發布日、有效期、正文／圖像／表格定位、驗證狀態 |
| service_calendar | route_variant、方向、service_day_type、valid_from/to、例外日期、來源 |
| operational_event | published_at、known_at、effective_start/end、affected_trips/stops、條件、action、supersedes、review_status |
| service_rule | scope、vehicle/route/trip、參數、有效期、來源、confirmed/provisional/conflict |
| seat_inventory | trip_id、segment_id、effective_capacity、onboard、protected_future_boardings、release_policy |
| transfer_edge | from_stop、to_stop、walk_seconds、same_vehicle、accessible、有效期與來源 |
| fare_product | product_id、支付／票種、權益、次數、期限、年度、預約權利、適用區間 |
| source_conflict | 相關來源、衝突欄位、原因、人工決議、有效期間 |

座位限制以各路段為單位：`projected_onboard(segment) + protected_unboarded_using(segment) <= effective_capacity(segment)`。保留席位應依實際區間與核銷／釋位規則計算，已上車者只計入 onboard，不能整條線永久扣住，也不能和預約名額重複扣除。

預測特徵使用「預測發布當時已知的公告」，保留 published_at 與 known_at；今天看到的歷史頁內容不一定就是當時頁面版本，不可把事後補充說明洩漏到歷史回測。

衝突處理順序只作候選規則：有效且適用的特別公告 → 有生效日的路線／產品明細 → FAQ／總覽 → 行程建議／首頁宣傳。仍需檢查方向、產品、日期與業者，不是遇到較新頁就無條件覆蓋。未解衝突時顯示待確認，不讓 LLM 自行補完。

## 7. 可以開始與仍缺少的資料

**現在可開始**：原始網站知識庫、圖表與班表的資料編目、子線拓撲草稿、2025-07-07 停駛標記、有來源 FAQ、票價／產品版本表、候補與座位保留的示例模擬。

**還需補齊才能作可信的現場決策**：站點座標與歷史版本、計費站對照、實際車輛乘客席數、駕駛勤務、完整歷史班表及加班車、GPS／實際旅行時間、預約與核銷資料、現金票與套票旅次涵蓋、候車／拒載觀測、能源與成本。

官網沒有提供可供本次使用的乘客預約後台、即時餘位 API 或能源數據；有公開訂票入口不代表已取得系統整合權限。

## 8. 驗收新增案例

- 2025-07-07 停駛日不被當作正常零需求訓練樣本。
- 國道服務不允許以站立容量安排乘客。
- 同一份預約保留名額不能扣兩次；逾時候補的釋位時間需由規則控制。
- 不把九人座車型字樣直接填成 9 個可售席位。
- 不同日期／方向／子線／車型的規則不串用。
- 公車動態沒有回報加班車時，不自動判定停駛。
- 套票無座位保障時，客服回覆不能承諾有位。
- 未解的泳渡臨時站點或商品價格衝突，不能直接發布旅客可執行指引。
- 無障礙方案同時檢查車輛、站點、輪椅空間及報到條件。
- 所有建議能回溯到來源與適用日期；過期／未知資料可見。
