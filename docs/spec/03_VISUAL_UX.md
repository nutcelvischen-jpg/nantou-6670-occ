# 03｜視覺化、GIS、畫面與互動規格

這是產品畫面規格提案，並非已建置畫面。主模式 Operate；每張圖必須協助觀察、選取、比較或決策，裝飾動畫不算視覺化完成。

## 1. 視覺方向與設計 token

概念：「交通營運桌上的地圖、班表與方案推演」。地圖占主要面積，時間軸與站點細節可收折；使用清楚數據標示，避免整頁發光、透明玻璃與大量同形 KPI 卡。

| token | 建議值 | 用途 |
|---|---|---|
| background | #F4F6F4 | 淺色分析底 |
| surface | #FFFFFF | 面板與表格 |
| ink | #172B2A | 主要文字 |
| muted | #596B69 | 次文字，需實測對比 |
| border | #D6DEDA | 分隔與表格線 |
| accent | #146B5A | 選取、主要操作 |
| baseline | #526D82 | 原方案 |
| candidate | #147D64 | 候選方案 |
| warning | #9A6700 | 警示與未知待核對 |
| danger | #B63B43 | 超限／無解 |
| assumed | #785CA6 | 假設資料標籤 |

字體：system-ui、Noto Sans TC fallback；內文14–16px、控制14px、圖標籤12px以上；數字 tabular-nums。不要以顏色唯一表意。圖表中的 red/green 同時附圖形／文字／正負值。

間距4/8/12/16/24/32；互動按鈕至少40px高，手機44px；focus outline ≥2px。配色與尺寸是提案，落地須檢查 WCAG AA 對比、鍵盤可操作性及200%縮放。

## 2. 全域結構

1440×900：左導覽72–200px可折疊、頂工具列64px；主區以地圖／工作區為中心。主畫面右詳情360px、底時間帶180–240px，可收折。1280px：右詳情變320px；不足1024px改抽屜。390px旅客頁單欄；營運頁可看簡版地圖與清單，複雜調度顯示需桌面編輯。

全域工具列固定：模式標籤、服務日期、路線／方向、資料版本摘要、資料狀態；右上只保留主要動作。不能將重要模式藏在設定頁。

## 3. 共用視圖狀態與連動

`ViewState = {mode,service_date,version_ids,pattern_ids,direction,time_range,sim_time,run_id,selected_stop_id,selected_trip_id,comparison_run_ids,layer_visibility}`。

- URL 保存可分享的聚合篩選與 run_id；不存卡號／Secret／個資。
- Query cache key 含所有影響數據的版本與篩選；舊查詢晚回不得覆蓋新篩選。
- selected_entity 用 stable ID，不用陣列索引。
- 拖曳時間軸改 sim_time，地圖、右側、圖表游標同步；不重跑模型。
- 修改情境參數只標 dirty；按「驗證並執行」才開新run，避免每拖一步都昂貴求解。
- 選一個圖表 bar／cell 時更新 shared selection，其他圖表高亮而非偷偷改分母；明確區分 highlight 與 filter。
- 返回上頁保留篩選；重設篩選與重設播放是不同操作。

## 4. GIS 圖層契約

| ID | 圖層 | 資料 | 編碼／互動 | 缺資料 |
|---|---|---|---|---|
| MAP-01 | 底圖 | provider style | 低飽和，站名與路網可讀；來源標示 | 空底圖＋可用 GeoJSON，提示底圖不可用 |
| MAP-02 | 子線／方向 | route_pattern shapes | 子線色＋方向箭頭；線寬固定，不以需求誤導路寬 | 站群拓撲示意，不假裝精確道路 |
| MAP-03 | 站點 | stops/fare_station | 實體站實心、代表點空心；點選詳情 | 不明座標顯示側欄清單 |
| MAP-04 | 需求熱圖 | 時段聚合 | 序列色階；legend 固定所比較範圍 | 灰色缺值，不用零藍色 |
| MAP-05 | OD | od_day / selected bin | 有向弧／粗細按流量；預設最多20對 | 說明計費站 OD 非實際軌跡 |
| MAP-06 | 車輛 | snapshot vehicles | 沿 shape chainage 插值；狀態圖示 | 重建虛線、live過期灰，不能當實測 |
| MAP-07 | 候車／未服務 | simulation station state | 比例圓＋數字；超門檻輪廓警示 | historical無觀測不顯示實測排隊 |
| MAP-08 | 載客 | segment load | 每段占比／未知容量用人數圖例 | 容量缺失不顯示百分比 |
| MAP-09 | 事件 | operational_event | 封閉段斜線、站點異動圖示、時間標籤 | 未核對改道只畫影響標記 |
| MAP-10 | 景點／步行 | POI,walk graph | 類型符號、營業狀態、合法步行路徑 | 無步行路網只給粗略距離不導航 |
| MAP-11 | 方案差異 | run A/B | 增班／刪班／移時分符號，成本按選取顯示 | 網路版本不同禁止直接逐段差值 |
| MAP-12 | 電巴／充電 | vehicles,charger | SOC／樁狀態，點選能源時間帶 | 未知樁不生成虛構位置 |

圖層預設只開底圖、選定子線、站點、車輛與一個需求／負載主題。OD、熱圖、載客層同時開易遮蔽，提供「需求」「乘載」「事件」「方案」預設組合。關圖層不改計算。

路線圖不是一般直線相連：有核對 shape 就沿 shape；無 shape 才顯示虛線拓撲＋「示意」。路線透明度依選取改變，不能代表未定義信心。

### 4.1 路線 3D 數位孿生視圖

第一版 3D 視圖以官方 TDX 子線 shape 投影至本地公里座標（約 1 場景單位 = 1 km；東西向使用中心緯度修正經度距離）；車輛沿 shape chainage 依固定步進模擬狀態移動。只有模型標記為營運中的車輛可出現在路線上並接受場景點選；待命車只在車隊清單／詳情顯示「待命」，不得畫成正在移動或顯示有效路線進度。子線 selector 必須以官方 `SubRouteName` 為值；方向對應方向 shape，無反向 shape 才可反轉同一 geometry 並標示降級。選車清單與場景點選共用穩定 `vehicle_id`，同時更新詳情、方向、載客率與路線進度。相機支援旋轉／縮放／重設；右側車隊卡可捲動。

- 頂部顯示官方／快取／示意資料狀態與「非即時 GPS」聲明；TDX 429／離線使用有效快取，否則退至拓樸示意並顯示原因。
- 場景路線與站點來源可為官方幾何；建物、道路外地形、湖面、高程與車身細節均屬視覺情境，標示為示意，不能暗示精密測量或實際建物模型。
- 車輛 Mesh 位置只讀同一 simulation snapshot；不得在場景端另算 KPI、乘客、成本或碳排。渲染端可在固定步階之間做不回寫模型的插值。
- 使用者點車後高亮對應 Mesh，顯示車型、方向、上車人數／容量、路線進度、累積車公里；不能把模擬載客值標成實測。
- 預設桌面 1440×900 場景高度約 60–70vh，車隊面板浮在右側；窄螢幕改為場景下緣車隊抽屜，避免遮住路線關鍵區。WebGL 不可用時保留資料面板並顯示明確降級訊息。
- 認證資訊只由後端持有；地圖瓦片 token 不放場景 URL 以外的記錄或文件。TDX 靜態 route/stop/shape 與 GPS/ETA live feed 必須分開標記。

#### 視覺呈現與場景生成

- 數位孿生工作台採使用者確認的淺色地理展示視覺：左側霧綠地形與等高線場景，右側白底營運指標與車隊狀態面板；路線使用藍／橘區分方向或能源車型，狀態必須同時有文字與顏色。僅在孿生頁套用此佈局，其餘分析頁面沿用共用淺色工作台主題。
- 桌面首屏順序為標題／資料狀態、情境與時鐘控制、車隊假設控制、五項營運 KPI、主要 3D 路廊與車隊面板。GIS、改善試算、時間序列及碳排圖表在 3D 場景之後；窄螢幕改單欄排列，控制與 KPI 不得被浮層遮住。
- 道路依官方 shape 繪製為可辨識的路帶，選定方向用亮色線條突出，回程方向降低亮度；站點採抽樣避免標籤重疊，選車時同步高亮清單、場景車輛及明細。
- DEM 未提供前，地景以固定雜訊種子、平滑格點雜訊與多倍頻 fBm 程序生成連續起伏，聚落以固定種子 InstancedMesh 依所選路廊建立示意群落。不得把程序地形、聚落、水面或其高度宣稱為真實地理測量。接入有授權的 DEM 後再以地形 raster/mesh 替換視覺替代層。
- 所有 KPI、圖表與車隊狀態都須在暗底上保持可讀；狀態不只靠色彩區分，保留文字／圖例。滑鼠、鍵盤焦點、暫停、載入中、TDX 失敗與 WebGL 降級狀態均需可見且有明確回復操作。

## 6. /operations 營運地圖

載入流程：先顯示版本摘要與可用日期→讀聚合→載路網→載所選時間快照。禁止先顯示demo數字再替換成真實。預設日期取最近一個品質合格歷史日，而不是今天配歷史資料。

主要流程：選子線方向→點站→顯示來源、上下車、適用班次與未知項→點「以此建立情境」複製當前版本與篩選。站點詳情四欄：觀測需求、供給、規則、情境結果；不把觀測與模擬相加。

選車時：班次、車型、路段、在車量、保留未上車量、可分配餘裕、來源。容量未知則「容量待確認」；時段外顯示 off_service，不隱藏累積里程。

## 7. /demand 運量分析

上方用CH-01＋CH-02，主區CH-03，底部趨勢與預測。固定維度篩選：日期範圍、子線、方向、票種、站群。資料粒度 15m／60m／day 切換；大範圍自動建議較粗粒度，但需使用者可見且記錄。

「尖峰」可選每日前20%時段或固定時段；定義顯示於圖標題，不能不同頁暗用不同閾值。「乘客」字樣僅在確認一列一人且去重後使用，否則「票證交易」或「估計搭乘」。

行為頁不用單卡詳細地圖；呈現聚合群與樣本量。小群遮罩不可透過tooltip洩漏。

## 8. /scenarios 情境實驗室

左側參數分三組：需求（倍率／時移／到站分布）；供給（可用車／候選班次／容量／保留政策）；事件（時間窗／路段／延誤／取消）。進階區才放 seed、cost profile、solver policy。

右側GIS，中下方事件軌與車輛甘特。數值輸入附單位、來源、範圍；從觀測改成假設時顯示 assumed。

| 動作 | 行為 |
|---|---|
| 建立／複製 | 新 scenario_id；名稱預設可改；原run不變 |
| 編輯 | revision遞增，dirty標記；無效整批拒絕 |
| 驗證 | 回缺件、範圍、規則衝突，不開始運算 |
| 執行模擬 | 202＋job；進度有stage與已處理模擬時間 |
| 求最低營運成本 | 顯示目標、服務底線、候選範圍確認摘要，直接提交授權範圍內工作 |
| 取消 | 切cancel_requested→cancelled；已完成結果不能誤刪 |
| 比較 | 選兩個相容run；不相容列差異與不可比原因 |

操作情境不要求再次批准才能算；「採用」只是記錄偏好，不對外派車。

## 9. /optimization 方案比較

第一區用成本、服務達成、求解狀態、資料階梯四個文字摘要；主區CH-09與CH-08；右側方案差異；下方班表與甘特圖。

候選表欄：方案、營運成本、未服務、p95已上車等待、期末排隊、車公里、排放、solver狀態、模擬驗證、勤務檢核。排序預設「符合服務且模擬通過者，成本由低到高」，失敗與未驗證另列不混排。

最便宜被拒方案也可檢視：顯示因容量／末班／服務底線失敗。最佳解標章必附「候選集合內」或「目前找到」；solver timeout不能標綠色optimal。

## 10. /journey 旅客行程

輸入起訖、日期、最早出發／最晚抵達、票種、已持票券、最多換車／步行、無障礙。預設主tab最低票價；最快、最少換車各自計算。

結果先顯示實付總額、抵達、總時長、換車、餘位狀態。每段時間帶列乘車站、方向、班次、步行與緩衝、該段收費。不得以企業成本金額冒充票價。

原始票券價格若為既有支出，顯示「已有票券，本次新增支出0」並列原購價未知或已知；不要把套票免費描述成整趟零成本。

票價未知：保留時刻方案，費用顯示待確認，無「最低」標章。沒方案：分別顯示錯過末班、轉乘時間不足、票種不符、無障礙未知、資料不足；不以空白地圖結束。

旅遊P1：先規劃回程限制，再插入景點與停留時間。景點排序變更才重算行程；不能把線性距離當步行時間。客服區可解釋目前行程，引用來源與日期，不自動下單。

## 11. /green 低碳頁

並列「能源活動數據」「係數」「排放邊界」；成本在獨立圖，不把kg當錢。柴油與電巴比較必須同路程／需求，且電巴SOC未驗證時顯示能源比較而非可執行方案。

年度係數切換生成新估算版本，顯示這次差異是電力係數、車型效率還是里程／載客所致。CH-12分直接燃料與間接購電；全生命週期未納入則明示。每人公里分母為0時顯示不適用。

敏感度至少：油價、電價、能耗、電力係數、載客、空駛比例。不要預置「減碳30%」；所有差異由模型計算。

## 12. /data 資料中心

來源表→解析→映射→品質→發布，各步狀態可回溯。點問題行可看去識別的原始欄位與來源定位，不顯示卡號。發布新版本前列受影響計算與未解衝突；已發布版本不可覆寫。

官網來源不嵌入可執行HTML；只顯示清理後文字／本機圖像及原站連結。匯出紀錄包含來源文件與版本，無關來源不外傳。

## 14. 可及性、效能與動畫

鍵盤可選清單替代地圖點選；地圖之外有文字行程／站點摘要。prefers-reduced-motion 關閉車輛平滑與過場，仍同步狀態。tooltip可鍵盤focus觸發；所有單位可朗讀。

一般UI過場150–250ms，播放只反映時間／狀態。無裝飾背景粒子。車輛超過500先聚合或視窗裁切，無強制每車DOM marker；線圖降採樣但保留尖峰與原始查詢。地圖移動debounce約200ms，拖時間軸預覽節流約100ms（ASSUMPTION），放手取最終快照。

## 15. 視覺完成定義

至少看過1440×900、1280×800、390px旅客頁；驗證可讀圖例、長站名、無資料、API失敗、低速網路與WebGL不可用。操作一次情境→GIS／甘特／成本／排放同步同run_id。所有圖表附數據表或下載，顏色不作唯一辨識。

## 16. 營運優先資訊架構

導覽按工作任務排序，而不是按技術模組排序：「營運總覽、需求預測、票證分析、數位孿生、班次最佳化、情境比較、智慧小幫手、資料品質」。前三個工作台頁面優先呈現；低碳評估、旅客行程及內容管理收在次要區。每頁沿用全域模式標籤：歷史、情境模擬、即時。即時模式只有在 feed 健康且資料未過期時可選；否則顯示停用原因與最近可用資料時間。

### 16.1 營運總覽（首頁）

首頁是值班／規劃者的操作桌面，桌面版由四層組成：

1. 頂列篩選：模式、日期／時間、6670子線、方向、資料版本；右側顯示來源新鮮度及「詢問小幫手」。預設使用最近一個資料品質合格的歷史日，不能用今天的日期搭配歷史資料冒充即時。
2. 四個摘要：票證交易量、尖峰小時與時段定義、相較基準期的需求變化、目前資料／事件狀態。每張摘要可點進對應分析，不使用無來源的「營運健康分數」。
3. 主工作區：左側約三分之二為地圖或 3D 場景，右側為「需要留意」清單。地圖以一致形狀標出需求、車輛／模擬車輛、服務事件和站點；右欄每一筆列出影響子線、時間、證據、嚴重度與資料品質。即時地圖缺 feed 時改顯示官方靜態線形，不顯示移動車輛。
4. 下方分析帶：需求實際值與預測區間、尖峰站點排名、供需差距／候選班次概況。各圖共用目前的時間和子線篩選；點圖表只做跨圖 highlight，除非使用者明確套用篩選。

視覺主題以明亮、易讀的 GIS 控制室為底；3D 孿生採獨立深色沉浸視圖，提供「回營運總覽」入口。3D 用於看路線空間、車輛狀態和情境差異；精確數值仍在圖表、表格和詳情面板呈現。

### 16.2 需求預測與票證分析

需求頁依序呈現「預測 vs 實際時間序列（帶預測區間）」、「星期×小時熱圖」、「子線／方向篩選」、「模型回測卡」。回測卡至少列資料期間、訓練截止日、WAPE、MAE、樣本數及相對基線的改善；若沒有可信提升，顯示目前使用統計基線。預測圖標題直接標明目標欄位是交易數或估計搭乘，不能默稱全體乘客。

票證頁將尖離峰作為首頁視覺：上方顯示明確尖峰定義與適用期間；中段放按日型切分的 24 小時交易曲線和方向／子線熱圖；下段放 OD 矩陣、票種分布、年／日交易量和頻次分桶。卡號只在本機批次被轉成匿名聚合，小樣本遮罩，前端和 LLM 都不可取得原始卡號。OD 必須標成計費站推估起訖，並提示它不等於精確上車站／下車站。

### 16.3 班次最佳化和情境互動

最佳化頁先要求使用者選需求情境、最低服務頻率／未服務上限、可用候選班次和成本版本；「執行」前用短摘要複述固定輸入與限制。結果首屏顯示求解狀態（optimal／feasible／infeasible）、目標成本、下界／gap、資料階梯和涵蓋範圍；其後才是成本瀑布、服務水準、車輛甘特及候選方案表。最佳方案明確標「此候選集合內」，不得推廣成整體車隊全域最優。

點選候選方案時，地圖、站點面板、甘特、成本和需求差異需以同一個 run ID 聯動。情境修改先標記待計算；按「驗證」只檢查資料和限制，按「執行比較」才啟動模型。模型輸出只是假設方案，頁面不提供實際派車或調班按鈕。

### 16.4 智慧小幫手：旅客與營運工作台

小幫手由全站固定入口開啟右側抽屜；在獨立助理頁可放大閱讀。第一次開啟讓使用者選「旅客資訊」或「營運分析」，並以不同範例提示問題。使用者可用自然語言問：「現在 6670A 有沒有延誤？」、「今天哪個時段需求最高？」、「埔里到高鐵的班次／末班資訊？」、「若尖峰需求增加 15%，目前候選班次會缺多少座位？」。第二類情境問題必須標示模擬輸入並呼叫指定計算服務。

回答版型固定為：一句話結論、資料狀態 chip、查詢範圍、證據／計算卡、下一步。證據卡顯示來源、時間戳、生效日期、資料品質（觀測／衍生／假設／過期／缺失）和「查看資料」連結。當來源不支持即時狀態，回答必須明確說「目前沒有可確認的即時車況資料」，提供官方班表／客服等已核實替代資訊；不得由模型猜測延誤、餘位或末班有效性。

使用者回報「車沒來／延誤／搭不上」時，助理先確認路線、方向、站點和預計時間，再按序檢查：該日期班表是否適用、是否有已發布公告、即時 feed 是否在線及其最後更新時間、同一時段是否有可查替代班次。每步列出查到的證據；沒有公告或 feed 時只說「未查到可驗證事件」，不推論沒有事故。最後提供可行的下一步，例如查看已核實班表、聯絡業者或改查其他日期／方向；不替使用者取消、改票或通知業者。

建議的後端流程：瀏覽器傳送文字、工作模式、目前頁面篩選和 request ID；後端先依登入角色與模式建立允許的 tool 清單，再由 OpenCode 模型輸出受 schema 約束的意圖和參數；後端驗證參數後呼叫唯讀查詢或命名的 forecast／optimization preview；最後模型只摘要已回傳的結果並附來源。瀏覽器不持有 OpenCode key。工具初版只包含 `get_service_status`、`get_timetable_snapshot`、`get_demand_aggregate`、`get_forecast`、`preview_fleet_optimization`、`get_source_health`；不提供通用 SQL、shell、Python、URL fetch 或外部寫入工具。

如使用者要求重跑預測／最佳化，助理先顯示輸入與限制摘要，使用者按「執行情境」後才送出 job。即使按下確認，動作也只產生可檢視的本機／後端 scenario run，不會修改正式班表或派遣車輛。若工具失敗，回答顯示 request ID、失敗來源和重試入口，不補造答案。

Sites 前端部署時，前端只需設定自有 API base URL；OpenCode key 和系統提示詞留在後端 Secret。API 尚未提供時可用本機 fixture 呈現 loading、empty、stale、error、缺即時資料等狀態，並在頁面標記「示範問答」，不得假裝模型已連線。

手機版小幫手採全螢幕對話頁；資料引用可展開，快速問題以可橫向捲動 chips 呈現。讀屏器應朗讀來源狀態，鍵盤可從回答移至引用和操作按鈕；車況狀態不能只靠綠／紅色點表示。
